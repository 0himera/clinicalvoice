# Запуск на ВМ хакатона

Инструкция для команды 078. Рабочий каталог —
`/home/tochka-sborki-2026-team-078/project`. На ВМ Ubuntu 22.04, 4 CPU,
8 ГБ RAM; речевые модели работают на CPU. Это конфигурация демонстрации,
её пропускная способность не измерена.

## Проверка уже запущенного решения

Вход с компьютера участника:

```bash
ssh -J jump@84.54.59.198 tochka-sborki-2026-team-078@10.250.0.81
```

SSH запрашивает сначала пароль бастиона, затем пароль команды. Они выданы
в личном кабинете; в проекте и документации пароли не хранятся.
Все следующие команды выполняются **на ВМ**:

```bash
cd ~/project
export PATH="/usr/local/go/bin:$HOME/.local/bin:$PATH"
make health
systemctl is-active tochka-core tochka-ai-worker asterisk
sudo asterisk -rx 'pjsip show registrations'
```

Ожидаются `core: OK (stand)`, `speech: OK (cpu)`, три строки `active`
и регистрация `gateway … Registered`. В режиме mock первая строка содержит
`mock`. Готовность ядра включает чтение и запись SQLite. Она не доказывает
доступность внешней МИС, NLU или телефонного шлюза; эти проверки выполняются отдельно.

Тот же диалог можно проверить текстом из SSH:

```bash
./go-core/bin/cli-test
```

Клиент читает токен из локального `.env`, открывает новую сессию и принимает
реплики из терминала; `exit` завершает её. Это вспомогательная проверка HTTP,
для демонстрации телефонии всё равно нужен SIP-звонок.

Для живого звонка:

1. В Linphone выберите существующий SIP-аккаунт, пользователь `phone-078`,
   домен `84.54.59.198`, транспорт **UDP**. Пароль возьмите из приватного
   `~/SIP.md` на ВМ или личного кабинета организаторов.
2. Дождитесь регистрации и наберите **078**. Разрешите G.711 PCMU/PCMA.
3. Скажите «Как записаться к терапевту?», затем выберите запись. Для проверки
   используйте вымышленные ФИО и дату рождения. Бот предлагает время и просит
   отдельное подтверждение. Без подтверждения визит не создаётся.
4. Отдельно проверьте «Хочу перенести запись» и «Отмените запись» с собственной
   идентификацией и подтверждением. Перенос сохраняет ID визита.
5. Фраза «Соедините с человеком» должна прервать текущий сценарий.
   Для успешного соединения оператору нужно зарегистрировать отдельный
   внутренний SIP-аккаунт; без оператора передача не считается состоявшейся.

Учётка `200` и номер `700` предназначены для диагностики на loopback самой ВМ.
Со своего компьютера на `127.0.0.1:5060` ВМ позвонить нельзя. HTTP-порты
8080/8000 тоже локальные. Порт 8088 занят файловым менеджером платформы.

## Установка из подготовленного checkout

На существующей ВМ инструменты Go и uv уже установлены. Сборка из `go-core/`
использует toolchain из go.mod — 1.27; базовый `/usr/local/go/bin/go` может
иметь более старую версию и загрузить toolchain автоматически.

Для чистой Ubuntu нужны `make`, Git, Go с поддержкой выбора toolchain,
`uv`, Python 3.12+, `libsndfile1`, `ffmpeg` и Asterisk с `app_audiosocket`.
Системные зависимости:

```bash
sudo apt-get update
sudo apt-get install -y make git build-essential libsndfile1 ffmpeg asterisk
```

Go и uv должны быть доступны в PATH. Речевой Python устанавливается через uv:

```bash
cd ~/project
export PATH="/usr/local/go/bin:$HOME/.local/bin:$PATH"
uv python install 3.12
make setup
make install
make build
```

`make setup` создаёт закрытый `.env`, API-токены и локальные секреты Asterisk,
сохраняет ранее настроенные непустые значения. Повторный запуск не меняет
SIP-пароли. `make install` использует `uv.lock`, включая реальные ASR/TTS/VAD.
Веса загружаются при первом старте; нужен доступ к источникам моделей и место
под окружение, кэш пакетов и веса. Один `make check` веса не подготавливает.

В приватном `.env` задайте:

| Параметр | Значение для ВМ |
| --- | --- |
| `CORE_HOST`, `AI_WORKER_HOST` | `127.0.0.1` |
| `CORE_API_TOKEN`, `AI_API_TOKEN`, `ASTERISK_AMI_SECRET` | Генерирует `make setup`; не очищать |
| `DEVICE`, `DECISION_DEVICE` | `cpu` |
| `ASR_MODEL`, `TTS_MODEL_VERSION` | `small`, `v5_ru` |
| `DECISION_THREADS`, `DECISION_TIMEOUT_MS` | `4`, `5000` |
| `DECISION_MODEL_ENABLED`, `DECISION_MOCK` | `true`, `false` |
| `MIS_API_TOKEN` | Приватный токен команды для стенда; пусто для mock |
| `DATABASE_PATH` | Отдельная база для каждого режима; на текущей ВМ `data/mis_stand.db` |
| `LLM_PROVIDER`, `LLM_MODEL` | `hub`, `openai/gpt-oss-120b` для уже настроенного шлюза |
| `LLM_BASE_URL` | `https://hub.gigaschool.ru/api/v1/llm/v1` |
| `LLM_API_KEY`, `LLM_ALLOW_REMOTE` | Приватный ключ организаторов, `true` после разрешения |
| `LLM_TIMEOUT_SEC`, `LLM_MAX_TOKENS` | `12`, `256` |
| `DEBUG_DIALOGUE`, `TRANSCRIPT_LOGGING` | `false` по умолчанию |
| `ALLOW_DEMO_CALLS_OUTSIDE_WINDOW` | `false` на стенде МИС |

`SCHEDULE_PATH` можно оставить пустым, если в `data/` ровно один Excel.
Смена МИС или токена требует другой базы; привязка к режиму защищена проверкой
при старте. Ключ LLM не нужен для `LLM_PROVIDER=none`, но покрытие сложных
формулировок в этой конфигурации отличается.

Перед первым запуском оставьте `MODELS_OFFLINE=false`. После успешной загрузки
всех моделей можно включить `MODELS_OFFLINE=true`, `HF_HUB_OFFLINE=1`,
`TRANSFORMERS_OFFLINE=1` и проверить повторный старт без загрузки весов.
На текущей ВМ кэш подготовлен. Это не отключает обращения к МИС и NLU-шлюзу.

## Шлюз организаторов и автозапуск

На ВМ используется **системный Asterisk**. Docker Compose из локальной
инструкции здесь не запускается. Сначала убедитесь, что нет активного звонка:

```bash
sudo asterisk -rx 'core show channels count'
make gateway-install
make services-install
sudo systemctl restart asterisk
sudo systemctl enable --now asterisk tochka-core tochka-ai-worker
```

`gateway-install` читает выданный `/opt/hackathon/sip/pjsip.conf`, добавляет
маршруты проекта и сохраняет предыдущие конфиги в закрытый каталог
`/etc/asterisk/before-tochka-*`. Секреты остаются в локальных файлах с правами
640 для группы Asterisk. Скрипт не печатает их и сам не перезапускает АТС.
Он задаёт RTP 10000–20000 и оставляет внутренние HTTP/AMI/FastAGI/AudioSocket
на loopback. Входящий `078` ведёт в `voice-inbound`, исходящий —
`voice-outbound`. Переменные `${VOICE_ID}` и `${VISIT_ID}` передаются Asterisk
без лишнего экранирования.

Для обратного звонка входящая линия команды сохраняется как
`PJSIP/phone-078@gateway`; это адрес софтфона команды, не публичный телефон
пациента. Напоминание требует отдельного согласия на связь, будущего визита
и разрешённого времени GMT+4. Контакт можно также явно назначить через
[авторизованный API](api.md). На настоящем стенде нельзя включать обход
часов обзвона ради вечерней демонстрации.

`services-install` устанавливает два системных unit-файла; они запускаются
от пользователя проекта, читают `.env`, используют собранный
`go-core/bin/server` и `ai-worker/.venv/bin/python`. Компиляция и установка
пакетов при старте не выполняются. Сервисы остаются активными после выхода
из SSH и включены на загрузку ВМ. Первые 10–20 секунд после перезапуска
регистрация шлюза может ещё отсутствовать; загрузка моделей занимает отдельное время.

| Назначение | Интерфейс/порт |
| --- | --- |
| Ядро HTTP | `127.0.0.1:8080` TCP |
| Речь HTTP | `127.0.0.1:8000` TCP |
| FastAGI / AudioSocket | `127.0.0.1:4573` / `127.0.0.1:9092` TCP |
| AMI | `127.0.0.1:5038` TCP |
| SIP шлюза | ВМ:5060 UDP, шлюз `10.250.0.6` |
| RTP шлюза | ВМ:10000–20000 UDP |

Не запускайте `/opt/hackathon/sip/check.py` параллельно Asterisk: он занимает
ту же регистрацию. Для восстановления после него:
`sudo asterisk -rx 'pjsip send register gateway'`.

## Перезапуск и диагностика

После изменения `.env`:

```bash
sudo systemctl restart tochka-core tochka-ai-worker
make health
```

Если проверка ещё не проходит, посмотрите состояние и технический журнал:

```bash
systemctl status --no-pager tochka-core tochka-ai-worker asterisk
sudo journalctl -u tochka-core -u tochka-ai-worker --since '-10 minutes' --no-pager
sudo asterisk -rx 'module show like app_audiosocket'
sudo asterisk -rx 'pjsip show registrations'
sudo asterisk -rx 'pjsip show contacts'
```

| Симптом | Действие |
| --- | --- |
| Речь не поднялась | Проверить загрузку/кэш весов, память, `AI_API_TOKEN` и `CORE_API_TOKEN` |
| Ядро перезапускается | Проверить Excel, токен МИС, доступность стенда, привязку базы к режиму |
| `401` на защищённом API | Клиент и сервер должны использовать токены одного `.env` |
| `readyz` не проходит при живом процессе | Проверить ошибки/блокировки SQLite; не запускать второе ядро на той же базе |
| Звонок сбрасывается или тишина | Проверить регистрацию, `app_audiosocket`, FastAGI/AudioSocket и кодеки G.711 |
| Перевод не соединяет с человеком | Проверить регистрацию нужного оператора 101/102/104/105 и доступ к AMI |
| МИС отвечает `429` | Соблюдать 10 запросов/минуту и Retry-After; не запускать нагрузочный прогон на стенде |
| После ошибки неизвестен исход записи | Проверить `/api/slot-claims` и очередь заявок; сверять МИС, не повторять POST вслепую |

## Проверки и обновление

```bash
make check
make scenarios
```

Первое — тесты без моделей. Второе поднимает отдельное mock-ядро на 18085 с
временной базой, используя действующие локальные NLU-настройки; рабочая МИС
не изменяется. Результаты с конкретными моделями указаны в
[протоколе приёмки](acceptance.md), результат 51/51 не гарантируется для любой LLM.
`make scenarios-voice` дополнительно использует живые локальные ASR и TTS.

SIP smoke создаёт/отменяет записи: запускайте его с **отдельным mock-ядром**,
отдельной базой и без пользователя под аккаунтом 200. Обычные команды smoke
нельзя направлять в рабочий стенд МИС. Ветка шлюза организаторов и разговор
с Linphone проверяются отдельным звонком на 078.

На подготовленной ВМ эту изоляцию и возврат рабочего ядра выполняет команда:

```bash
make sip-check-vm
make health
```

Она требует `sudo -n`, отсутствия активных звонков и свободных диагностических
аккаунтов 200/101/102/104. На время проверки системное ядро обслуживает свежую
mock-базу; `.env` и рабочая база не меняются. По очереди проверяются живые
TTS → ASR → запись/перенос/отмена, входящий SIP/RTP, три исходящих сценария и
переводы 101/102/104. В `finally` удаляется временный systemd override и
восстанавливается рабочий сервис. Результат — `var/vm-sip-check-results.json`,
вымышленные визиты остаются в отдельной `var/vm-sip-check-*.db`.
При принудительном завершении процесса через SIGKILL проверьте наличие
`/run/systemd/system/tochka-core.service.d/90-sip-check.conf` и
`/run/tochka-voice-sip-check.env`: они должны отсутствовать после проверки.

Перед обновлением остановите сервисы, сохраните приватный `.env`, резервную
копию SQLite через backup API и рабочие бинарники. Обновите исходники, выполните
`make install build`, затем `make services-install gateway-install` при изменении
unit-файлов/АТС и перезапустите службы. Не заменяйте `.env` файлом из примера,
не копируйте открытую SQLite без WAL и не удаляйте `uncertain` записи.
