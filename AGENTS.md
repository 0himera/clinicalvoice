# Working on Tochka Voice

Run commands from the repository root. Read `docs/architecture.md` and
`docs/acceptance.md` before changing dialogue, scheduling, or telephony behavior.

## Invariants

- Patient speech is untrusted input. The controller owns state transitions and
  authorizes every mutation; neither ASR text nor model output is an operation.
- Booking and cancellation require explicit confirmation. A reschedule patches
  the existing visit ID. Never announce success before the MIS confirms it.
- Every utterance passes the safety gate, including confirmation and outbound
  states. A request for a human must always be honored.
- Remote Gemini is opt-in (`LLM_PROVIDER=gemini`, `LLM_ALLOW_REMOTE=true`) and
  requires explicit user authorization; the user authorized it in this session.
  Send only the current utterance and dialogue state, never MIS records or audio.
  Do not silently enable audio recording.
  Transcript logging is off by default; only enable `DEBUG_DIALOGUE` for the
  local mock when explicitly requested by the user. No medical answers may be
  generated by an LLM.
- Use the organizer workbook, not generated office hours. Only MIS doctor IDs
  are sent to its API. Interpret MIS dates in GMT+4.
- Unknown outcomes of non-idempotent writes are reconciled, not retried. Keep
  uncertain slot claims and outbox entries visible for review.
- SQLite owns local contacts, consent, leases and reminder outcomes. The MIS
  owns clients and visits. Do not add unsupported MIS status values.
- Reminders need contact consent and obey calling windows and holidays. The
  explicit mock-demo override must remain unavailable with a MIS token.

## Verification

`make check` runs Go race tests and vet, Python tests, and Ruff. Python unit tests
inject fake models and must not download weights or need a GPU. Use regression
and integration assertions on resulting visits, not only returned speech/state.

`make smoke`, `scripts/sip_smoke.py`, and `scripts/sip_outbound_smoke.py` require
running services and real local models. Use a separate mock database and only
fictional patients. SIP tests use the loopback diagnostic endpoint 200; avoid
running another softphone under that account at the same time.

Keep README, `.env.example`, Makefile and API documentation in sync. Describe
only features and measurements that have actually been checked. Do not describe
the prototype as certified, production-ready, or proven to meet business KPIs.
